# Visualize Code Flow

実コードを読むための地図を作る。見栄えより、処理の順番、責務の境界、並行する流れ、状態の変化を一度で追えることを優先する。

## 入力を決める

会話とリポジトリから、次の2点を先に解決する。

- 対象: 追跡する機能、処理、module、path
- 問い: 読み手が理解したい流れや判断

両方が分かるなら質問せずに進む。図の構造が変わる不足だけが残る場合は、現在の推測を添えて一問だけ確認する。5W1Hを一通り聞かない。

## コードを追う

対象の project instruction を先に読む。その後、入口から出口まで実ファイルをたどる。

1. command、API、event、file などの入口を特定する。
2. 呼び出す function、module、adapter を追う。
3. 途中で変換する data と、保存する state を確認する。
4. 分岐、並行処理、再試行、feedback loop を見つける。
5. test、gate、CI がどこで結果を判定するか確認する。

node の名前には、確認した file、function、command、data artifact を使う。推測した関係は事実の線に混ぜず、必要なら注記として分ける。

## 図を組み立てる

全体を5〜7段階に分ける。入力、処理、保存、判定を同じ役割としてまとめない。

- 主な流れは左から右へ置く。
- 並行する処理は独立した水平レーンに置く。
- 同じ保存先や判定器へ入る線には、レーンごとの port を置く。
- connector は直線または直交線にする。斜線、交差、node の背後を通る線を避ける。
- feedback loop は図の外周を通す。主経路を横切らせない。
- node と線の間に十分な余白を取り、label を線上に重ねない。
- 一枚に複数の話題を詰め込まない。複雑なら全体図と詳細図に分ける。

色だけで意味を伝えない。レーン名、node 名、線の形を併用する。

## HTML にする

自己完結した HTML を作る。project に design rule があれば先に読み、その visual system に合わせる。

- 上部に段階を選ぶ control を置く。
- 選んだ段階を強調し、他の段階を薄くする。
- 選択中の段階を一文で説明する。
- 画面が狭い場合は縦方向へ並べ直す。
- title、説明文、node、control に accessible name を付ける。
- 外部通信を使わない。必要な data は HTML 内に置く。

図は調査結果に集中させる。長い解説、指標カード、検索、設定 panel を足さない。

## 表示を確認する

渡す前にブラウザで開き、次を確認する。

- 線が交差、重複、node や label を貫通していない。
- 同じレーンの node と port が同じ高さに揃っている。
- feedback loop が主経路の外側を通っている。
- 通常幅と狭い幅の両方で文字が切れない。
- 段階 control が動き、選択中の説明が変わる。
- console に error がない。

問題があれば、線を曲げて避ける前に node の配置と余白を直す。完成後は HTML をブラウザに表示する。

## 境界

可視化の依頼だけなら、対象コードを変更しない。保存先を指定されていない場合は project の生成物と混ざらない作業用の場所へ置く。安定した構造を documentation に残す場合だけ、ユーザーが指定した project path へ移す。
